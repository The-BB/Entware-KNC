    realtek: l3: trap main routes inside a local IPv6 prefix
    
    With more than one IPv6 table, the kernel also looks the local table up
    before main, so a local IPv6 prefix (AnyIP: ip -6 route add local ...
    table local) takes the destinations of a longer main route inside it.
    The switch matches the longest prefix and forwards them. Commit
    bf54d898c7 ("realtek: l3: trap main routes inside a local prefix") made
    such a route trap for IPv4 only.
    
    otto_l3_local_covers() now looks at local prefixes of both families. So
    that a local prefix that comes or goes is seen for IPv6 too,
    otto_l3_route_inside(), otto_l3_gw_seen() and
    otto_l3_local_prefix_check() take the struct fib_notifier_info both
    notifier infos start with, and tell the family from it. The IPv6 FIB
    work calls otto_l3_local_prefix_check() after an add or a delete, and
    the check no longer skips a prefix of length zero: otto_l3_fib_trap_v6()
    gives a local ::/0 a row, which otto_l3_local_covers() counts as
    covering every main route. An IPv4 local default route gets no row from
    otto_l3_fib_trap_v4(), so for it the check only resolves the gateways
    again and every route stays as it was. Without IPV6_MULTIPLE_TABLES the
    local routes are in main, where the kernel matches the longest prefix
    as the switch does, and they are not taken for local ones. Otherwise
    IPv4 behaves as before.
    
    Tested on a Hasivo S1100W-8XGT-SE (RTL9303), with 2001:db8:1:0:1::/80
    via a gateway on switch.3 and echo requests to eight addresses inside
    it captured at the gateway. With ip -6 route add local 2001:db8:1::/64
    dev lo table local, main kept the row forwarding and all 8/8 reached the
    gateway, whether the local prefix came before or after the route. With
    this change the row traps and 0/8 reach it, in both orders. Without the
    local prefix both forward 8/8. The same run of the IPv4 case traps on
    both, as before. That run predates the zero-length part. In a run of
    the final change, a local ::/0 made the row trap with 0/8 reaching the
    gateway, and once it went the row forwarded 8/8 again.
